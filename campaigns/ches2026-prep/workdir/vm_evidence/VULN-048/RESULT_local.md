# VULN-048: Ascon core/duplex no SVA assertions + reqParity ASSUME commented

## Verdict: **poc-success** (finding confirmed)

## Fidelity: L4 (static conclusion)

Pure oracle comparison — source code grep verification, no dynamic simulation.

## Summary

ascon_core.sv, prim_ascon_duplex.sv, and ascon.sv contain **zero** SVA functional
assertions. The only assertions exist in ascon_reg_top.sv (4 register-level assertions:
wePulse, rePulse, reAfterRv, en2addrHit). Additionally, the reqParity ASSUME in
ascon_reg_top.sv:2651 is commented out, disabling TL-UL request parity checking in FPV.

All sibling cryptographic IPs (AES: 5, KMAC: 3, HMAC: 2 assertions in their _core.sv)
have functional SVA. Ascon is the sole outlier with zero.

"this is formulated as an assumption such that the FPV testbenches do disprove this

is not enforced in any verification flow.

## Impact

- **No functional SVA** means no formal verification of Ascon correctness or security
  - No idle/done handshake checks
  - No key_valid gating assertions
  - No error propagation checks
  - No FSM state validity checks
- **Commented reqParity ASSUME** disables TL-UL request parity constraint in FPV
  - FPV can construct counterexamples with invalid TL-UL parity
  - Comment says it's to prevent FPV from "disproving by mistake" — but the proper
    fix is to refine the property, not disable it
- Verification gap: Ascon has no V2S-level assertion coverage for its security-critical
  AEAD cipher operations

### L2 Not Achievable — Reason

SVA assertion absence and ASSUME commenting are verification-structural properties. They have no I/O behavioral difference observable by Verilator simulation. An ASSUME is a formal verification constraint (FPV hint), not a runtime gate — commenting it out changes what counterexamples FPV can construct, not what the hardware does. Therefore L2 (micro-tb differential) is fundamentally inapplicable.
